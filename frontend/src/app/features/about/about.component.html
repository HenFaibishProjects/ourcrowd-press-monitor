Project Overview

A concise technical summary for reviewers.

What this project does

OurCrowd Press Monitor tracks press mentions for a curated list of OurCrowd portfolio companies. Manual and scheduled collection use the selected news provider, filter articles by relevance using a local model, classifies sentiment, and persists results to a relational database. A read-only Angular dashboard exposes the aggregated data by quarter.

Backend Node.js · NestJS
Frontend Angular (standalone components)
Database PostgreSQL
LLM Ollama (local, gemma3:270m)
Live provider GDELT DOC API
Demo provider FileNewsProvider (deterministic)

Architecture

A simple linear collection pipeline inside a single NestJS application.

→

Main decisions

Why NestJS

NestJS organizes companies, mentions, news, scheduling, and alerts into feature modules. Dependency injection keeps their boundaries clear inside one application.

Why PostgreSQL

PostgreSQL enforces relationships and UNIQUE(companyId, url), including duplicate insert races. Migrations define the schema, and Docker Compose provides the local database.

Why Ollama

The assignment requires local inference. gemma3:270m keeps it lightweight for reviewer machines. The model checks relevance and company-specific sentiment; its quality still needs evaluation.

Why GDELT

GDELT provides public news discovery without an API key. Real testing encountered rate limits and temporary failures. Requests use bounded retries and honor Retry-After.

Why FileNewsProvider exists

Verified fixture articles make discovery predictable for local review. They pass through the same CollectionService, local Ollama, and PostgreSQL persistence as live results. Supplied descriptions avoid publisher-page requests.

Why a modular monolith

One NestJS application is straightforward to run and trace. Feature modules keep responsibilities separate without adding deployment and network coordination between services.

If I were taking this further

The following were intentionally not included in this take-home. Each would be justified by a concrete scaling or reliability problem, not added upfront.

  • Queue / PubSub: decouple collection from API serving; enable dead-letter handling and retry visibility.
  • Worker-based processing: isolate inference and enrichment workloads from API serving.
  • Bounded concurrency: process multiple companies in parallel with a configurable concurrency limit, rather than strictly sequentially.
  • Distributed scheduling: use an external scheduler (e.g. Cloud Scheduler, pg-boss) so multiple replicas don't trigger duplicate runs.
  • Stronger observability: structured JSON logs, metrics (e.g. Prometheus), distributed tracing (e.g. OpenTelemetry).
  • Managed PostgreSQL: with connection pooling (PgBouncer), automated backups, and point-in-time recovery.
  • Better article extraction: a proper headless-browser fallback or a managed extraction service for paywalled or JS-rendered pages.
  • Labeled evaluation dataset: a human-labeled set of (article, company, expected-sentiment) triples to measure and iterate on model quality.

Reviewer quick start

Run these commands from the repository root. Docker must be running.

npm install
docker compose up -d
npm run db
npm run companies:setup
ollama pull gemma3:270m

# Deterministic demo run (FileNewsProvider):
npm run collect -- --companies=BioCatch --quarter=2026-Q3

# Start both servers in development mode:
npm run dev
